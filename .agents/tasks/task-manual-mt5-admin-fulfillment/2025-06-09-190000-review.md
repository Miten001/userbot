# Manual MT5 admin fulfillment replacing auto-provision

The auto-provisioning flow (mock MT5 provider creating accounts on payment) has been replaced with a manual admin workflow. Payment webhooks now only mark a challenge as "active"; a new admin API endpoint (`POST /api/admin/activate`) accepts MT5 credentials the admin sourced from the broker, inserts the account row, and emails the customer. The admin panel gains a "Pending Setup" section displaying all active challenges without a linked account, with inline input fields for login/password/server and an activate button.

**Watch for:** MT5 password stored in plaintext in the database (confirmed). Email notification failure is silent — admin gets a success response even when the customer never receives credentials (confirmed). No `profit_split_pct` set on account creation, which may break downstream payout calculations (likely).

## High-level view

The fulfillment pipeline splits into two phases: webhook marks the challenge active, and admin manually completes provisioning via a new dedicated endpoint. The activate endpoint stores the MT5 password in cleartext and the email notification is fire-and-forget with no feedback to the admin about delivery status.

The admin UI derives the "pending" list client-side by diffing challenges against accounts using `challenge_id`. This is coupled to the assumption that the admin overview endpoint always returns both full sets — its `LIMIT 100` means very old pending challenges could fall off the list.

<details>
<summary>Issues (4)</summary>

1. **Plaintext MT5 password in DB** — `mt5_password` is stored unencrypted in the accounts table. Encrypt at rest or at minimum use a server-side key so a database dump doesn't expose every customer's broker credentials.
2. **Missing `profit_split_pct`** — The insert omits this column; if the DB has no default, existing queries filtering or computing payouts by `profit_split_pct` will get null. Add it to the insert using the plan/step defaults.
3. **Silent email failure** — Admin sees "Account activated and email sent!" even when `notifyAccountReady` returns false. Surface the email delivery result so the admin knows to manually contact the customer.
4. **No state transition on challenge after provisioning** — Challenge stays "active" after account creation; there's no way to distinguish "paid, awaiting setup" from "paid, account provisioned" purely from challenge state. If accounts are ever deleted or the query fails, the challenge reappears in the pending list.

## Credential handling and storage

The activate endpoint receives `mt5_password` in the request body and inserts it directly into the `accounts` table. The response `.select("id, mt5_login, mt5_server")` deliberately omits the password — but the value sits in the database unencrypted. Any database breach or Supabase dashboard access exposes every customer's MT5 credentials. At minimum, the password should be encrypted with a server-side key before storage and decrypted only at email-send time.

## Missing `profit_split_pct` on account insert

The old auto-provision code inserted `profit_split_pct` but `stepRules()` doesn't return that field. The new activate endpoint doesn't set it either. The admin overview endpoint selects `profit_split_pct` in the accounts query, and the admin UI type definition includes it. If the DB column has no default, new accounts will have `null` for profit split, which may break payout calculations or display logic downstream.

## Email delivery feedback gap

```typescript
if (email) {
  await notifyAccountReady(email, { ... });
}
return NextResponse.json({ account });
```

`notifyAccountReady` returns `false` on failure but never throws. The activate endpoint ignores the return value. The admin panel toasts "Account activated and email sent!" regardless of whether the email went out. If Resend is misconfigured or the user has a bad email, the customer never gets credentials and nobody knows. Fix: capture the boolean, include `{ emailSent: true/false }` in the response, adjust the toast.

## Pending-list scaling assumption

The admin panel builds a `Set` of `challenge_id` from accounts and filters challenges where `state === "active"` and the id isn't in that set. The admin overview endpoint fetches only the last 100 challenges and 100 accounts. A challenge older than position 100 that's still pending (admin forgot about it) disappears from the pending list entirely.
