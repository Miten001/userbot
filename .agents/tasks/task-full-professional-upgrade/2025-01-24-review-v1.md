# Professional upgrade: routed dashboard, landing polish, theme system, and charts

This change decomposes a monolithic dashboard page into proper Next.js routed sub-pages (accounts, trades, payouts, settings), adds landing page enhancements (LiveTicker, Partners, VideoDemo), introduces a dark/light theme toggle via class-based Tailwind theming, adds a notification bell component, and introduces client-side SVG charts (EquityCurve, PnLChart) along with skeleton loading screens and page transitions. The implementation relies entirely on demo data when API calls fail, which means every page works without backend configuration.

**Watch for:** Chart SVG gradient IDs use `Math.random()` inside render, causing React hydration mismatches and new gradient definitions on every re-render (confirmed). The ThemeProvider renders children without context on first mount, so any child consuming `useTheme()` gets stale defaults during that frame (confirmed). Every dashboard sub-page independently fetches its own data from the same APIs, with no shared state or caching across the layout boundary (confirmed). Notification preferences on the settings page are purely local state — toggling them has no effect (confirmed, likely intentional for demo).

## High-level view

The dashboard split has a new `layout.tsx` that wraps all sub-pages in `DashboardLayout` and fetches the profile once, but each page independently fetches its own data from the API. This means four separate fetches to the same endpoints when a user navigates between pages. Going live with real API calls would produce noticeable loading spinners on every page transition.

The theme system uses `darkMode: "class"`, toggling `.dark` on `<html>`. Server-rendered HTML always starts with `class="dark"`, and the ThemeProvider reads localStorage after mount to potentially remove it. The approach avoids FOUC for the default dark theme but will flash dark-to-light for users who previously chose light mode. The light-mode CSS overrides only cover utility classes (`.glass`, `.lux-card`, `.btn-secondary`) — dashboard pages using inline Tailwind classes like `text-white` and `bg-bg-soft/50` will likely render broken in light mode.

The SVG charts are purely client-rendered with demo data generated via `Math.random()`. Chart data changes on every render/navigation, and the random gradient IDs inside the SVG will diverge between server and client if these components are ever included in a server-rendered path.

The sidebar uses `pathname.startsWith(item.href)` for active detection on sub-routes, but the Overview item (`href="/dashboard"`) would match every dashboard sub-route since they all start with `/dashboard`. The explicit `=== "/dashboard"` early return prevents this, but the logic is fragile — reordering conditions or adding a route like `/dashboard-settings` would break it.

## SVG chart stability and render performance

EquityCurve generates gradient IDs with `Math.random()` directly in the render body:

```tsx
const gradId = `eq-fill-${Math.random().toString(36).slice(2, 8)}`;
const lineGradId = `eq-line-${Math.random().toString(36).slice(2, 8)}`;
```

Each render creates new `<defs>` entries in the DOM. Old gradient elements get removed and new ones added, causing a brief flash during parent re-renders. React 18's `useId()` hook would produce stable, SSR-safe identifiers.

The same instability applies to demo data generation. `generateEquityData()` is called inline in JSX on the overview page — not memoized, not stable across renders. Every time a trade loads or profile state updates, the chart draws a completely different curve. In `trades/page.tsx`, the fallback functions also use bare `Math.random()`. The visual instability would confuse users who expect the chart to represent their actual equity once live data is connected.

## Theme flash and hydration gap

The root layout hard-codes `className="dark"` on `<html>`:

```tsx
<html lang="en" className={`${inter.variable} ${space.variable} dark`}>
```

ThemeProvider's `useEffect` reads localStorage and conditionally removes the `dark` class. For light-mode users, the sequence is: server renders dark → browser paints dark → useEffect fires → class removed → repaint light. A blocking inline script in `<head>` that reads localStorage and sets the class before React hydration would eliminate this flash.

The `if (!mounted) return <>{children}</>` guard means children render without real ThemeContext on first frame. The toggle button briefly shows the wrong icon (Moon instead of Sun for light-mode users).

## Light mode coverage gaps

The `globals.css` light-mode overrides target `.glass`, `.glass-strong`, `.lux-card`, `.btn-secondary`, and `.chip`. But dashboard pages use hardcoded Tailwind classes like `border-white/10`, `bg-bg-soft/50`, `text-white`, `bg-white/5` throughout. In light mode, this produces white text on a light background. The theme toggle effectively only works on the landing page; the dashboard would be unreadable in light mode without per-component `dark:` variants or CSS variable refactoring.

## Sidebar active state logic

```tsx
function isActive(item: NavItem) {
  if (item.href === "/admin") return pathname === "/admin";
  if (item.href === "/dashboard") return pathname === "/dashboard";
  return pathname.startsWith(item.href);
}
```

The second condition prevents Overview from lighting up on sub-routes via strict equality. But the third condition (`startsWith`) relies on the second condition having already returned for `/dashboard`. If a developer adds a new top-level dashboard route (e.g., `/dashboard-analytics`) without adding another special case, the `startsWith` logic would incorrectly match it against Overview's href. A trailing-slash check (`item.href + "/"`) or exact match for leaf routes would be more robust.

## Settings page: avatar and preferences have no backend

The avatar upload reads the file via `FileReader.readAsDataURL` into component state. The `saveProfile` function sends `full_name`, `country`, `phone` to `/api/profile` but never includes the avatar — no `FormData` POST, no upload endpoint. Users who upload a photo and save will lose it on reload.

Notification preferences (`emailNotifs`, `tradeAlerts`, `payoutNotifs`) are `useState(true)` with no persistence — not localStorage, not an API call. They reset to `true` on every visit. A disabled state or "coming soon" label would set correct expectations.
